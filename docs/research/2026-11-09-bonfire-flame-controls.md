# Bonfire flame controls — 9 November 2026

Private colour controls identify the source effect responsible for the visible bonfire
flame. A second control hides the other appearance layers while retaining one unchanged
layer. That layer supplies low flames around the logs; the tall flame and additional glow
disappear. Three source sessions exit normally. Across 2,705 observed light-buffer uploads,
the separate bonfire light retains its position, radius, colour relation and curve range.
Animation phase is not compared between launches.

The dependency reader resolves all six referenced textures directly from the source install.
Its first version missed numbered texture slots in the layered appearance. An independent
slot check rejects that version, then passes the correction. Repeated reads match all 17
output files. The source bundle fingerprint remains unchanged.

An isolated native-host atlas control uses the source texture, its frame sequence, base
dimensions and selected colour curves. It deliberately emits one stationary particle with
no random variation or inherited emitter transforms. This is a loading and visibility
experiment, not a translation of the complete source flame. Independent effect, texture and
map readback verifies the selected fields and every texture mip. Repeated builds match all
705 files; only the effect bundle and map change from the preceding illumination build.

The particle is not visually identifiable in the first host capture at the derived bonfire
attachment. Raising only its region clear of the logs produces a visible flame texture in
later frames. Its visible pixels lie inside the projected rectangle calculated from that
raised attachment and the camera. Early faint frames initially obscured this result; the
initial observation is retained alongside the correction. This confirms native loading
and rendering, without proving precise geometry, emission timing, blending or shading.
The raised placement is diagnostic and must not become the bonfire placement.

Both host sessions exit normally and restore the private camera profile. The existing
animated illumination runtime changes only its trace destination. Its lifetime checks pass
over 4,557 draws, and its light-position check retains the previous tolerance. An added
exact-equality check on the player anchor rejects ordinary collision settling; the camera
matrix is unchanged, and the existing capture anchor contract passes. Both checks are kept.
The golden host resting-point effect is still visible and remains work to remove.

Other retained failures include an isolation control that assumed every appearance had the
same alpha fields, and two unnecessary attempts to compile a separately inspected effect
library source. The corrected isolation handles both appearance shapes. Host writing reuses
the already installed library from the haze experiments. No failed compiler output is used.
An earlier executable-metadata investigation does not establish parent direction sampling;
that question remains open.

Next is the isolated source layer's emission, distribution, motion and attachment behaviour,
followed by the other layers and their shading. The full flame, activation lifecycle,
remaining host effects and broader visual fidelity are incomplete. The ordinary playtest
has not been promoted to either diagnostic build.

All game data, derived programs, third-party files, builds and captures remain outside the
repository. The existing private readers use SoulsFormatsNEXT under its recorded GPL-3.0
licence. The native writer reuses [EvenTorset's FXR library](https://github.com/EvenTorset/fxr),
version 32.1.3, under the [Unlicense](https://github.com/EvenTorset/fxr/blob/main/LICENSE).
Its public [build configuration](https://github.com/EvenTorset/fxr/blob/main/tsconfig-build.json)
was consulted during the unsuccessful compilation detour. This adds no production dependency
and does not settle the project's open language or licence decisions.
